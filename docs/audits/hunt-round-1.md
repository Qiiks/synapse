# Free-roam hunt, round 1

Findings are ranked by consequence.

## 1. Remote profiles fingerprint a tokenizer policy that serving never applies

- **Where:** `crates/synapse-module/src/remote/config.rs:282-320`, `crates/synapse-module/src/remote/gateway.rs:217-235`, `crates/synapse-module/src/remote/gateway.rs:480-487`, and `crates/synapse-module/src/remote/gateway.rs:811-823`. The promised behavior is also explicit in `docs/design-remote-gateway.md:55-66`.
- **Actual versus expected:** Configuration accepts any nonempty `input_profile_id` and includes it in `remote_profile_hash`, so the fingerprint claims that input processing is bound to that profile. Serving never consults `input_profile_id`: `embed` truncates with `split_whitespace`, and `execute_embedding_request` reports the same whitespace count as `real_token_counts`. The design says Synapse pre-truncates with its own tokenizer identified by `input_profile_id`. A reader can therefore reasonably expect two profiles with different tokenizer identities to preprocess differently and expect `max_input_tokens` and token disclosures to use the declared tokenizer, not word count.
- **Reachability:** **REACHABLE.** `SynapseHandler::handle` dispatches `embed.query`/`embed.batch` through `remote_embed_query`/`remote_embed_batch`; both call `RemoteGateway::embed`, which unconditionally takes the whitespace path. A configured profile such as a BPE tokenizer plus an input containing a long no-whitespace string reaches the mismatch without any fault injection.
- **Cost if it fires:** Silent vector-space identity corruption: the response is stamped with a fingerprint for preprocessing that did not occur. Inputs that fit by word count but exceed the provider's model-token limit can also be refused by the provider, while successful responses expose wrong token counts and false truncation disclosures. Persisting those vectors can drive wrong retrieval or reranking decisions under an identity consumers trust to be stable.
- **Confidence:** **High.** The only production references to `input_profile_id` are configuration/identity construction; the gateway does not read it. A black-box remote-profile test using two supported tokenizer profiles and punctuation/CJK/no-whitespace inputs would raise confidence to complete runtime confirmation.
- **Status:** **VERIFIED.** `dispatch_request` reaches `remote_embed_query`/`remote_embed_batch`, which call `RemoteGateway::embed`; `embed` calls `truncate_text`, and `execute_embedding_request` calls `whitespace_tokens`, while the only Rust reads of `input_profile_id` are configuration and identity construction. A fix is deferred because the repository defines no tokenizer-profile registry: either reject every profile except the implemented `whitespace-v1` policy (a config compatibility change), or add a profile resolver and tokenize/truncate with the resolved tokenizer (a new runtime/config surface).

## 2. Concurrent model loads can share and overwrite the same scratch package

- **Where:** `crates/synapse-module/src/lib.rs:4831-4837`, `crates/synapse-module/src/lib.rs:6023-6043`, `crates/synapse-module/src/lib.rs:6531-6559`, and `crates/synapse-module/src/lib.rs:14801-14805`.
- **Actual versus expected:** Each admitted `model.load` gets its own spawned task, but its scratch directory is named only from process ID and millisecond wall-clock time: `synapse-model-load-{pid}-{now_ms}`. Two tasks first polled in the same millisecond use the same `model.bin`, `tokenizer.json`, and `extra-N.artifact` paths. `File::create` truncates those shared destinations, so downloads can overwrite or interleave with one another; either task can later remove the directory while the other still uses it. A reader would expect each job's downloaded package to be isolated by job ID or a collision-proof temporary directory.
- **Reachability:** **REACHABLE.** Send concurrent `model.load` calls with distinct explicit `request_key` values. Each admission spawns independently, and Tokio's multithreaded runtime can poll both blocking download paths during the same millisecond. Legacy string file specifications (`crates/synapse-module/src/lib.rs:1514-1518`) do not require per-file digests, so digest checks do not always turn cross-job replacement into a clean refusal.
- **Cost if it fires:** At minimum, both production load jobs can fail after downloading large artifacts. In the digest-optional path, one job can ingest another job's valid model or tokenizer under its own requested model configuration, producing wrong-model execution or a later engine crash rather than a deterministic integrity error.
- **Confidence:** **High** for the namespace collision and truncation race; **medium-high** for silent wrong-model acceptance because engine/package validation may reject some mixed combinations. A barrier-controlled two-load integration test with valid same-format artifacts and legacy file specs would establish the exact terminal outcomes.
- **Status:** **VERIFIED.** `dispatch_request` calls `model_load`; each distinct admitted request receives a collision-resistant `job_id` from `new_job_id` and is independently spawned into `execute_model_load_job`, but the old scratch path ignored that ID. The fix keys scratch paths by the minted job ID. Mutation proof: `concurrent_model_load_jobs_use_distinct_scratch_paths` failed with `assertion left != right failed` when job IDs were removed from the path.

## 3. `cache.pin` does not participate in the lease that protects it from GC

- **Where:** `crates/synapse-core/src/cache.rs:255-260` and `crates/synapse-core/src/cache.rs:283-351`; production handlers call these paths at `crates/synapse-module/src/lib.rs:14059-14085` and `crates/synapse-module/src/lib.rs:14117-14137`.
- **Actual versus expected:** `gc_digest` acquires an exclusive digest lease before reading metadata and deleting the blob, but `pin` performs an unlocked read-modify-rename of the same metadata. GC can read an unpinned row, then delete the blob and metadata after a concurrent `pin` has returned success; the inverse interleaving lets `pin` recreate pinned metadata after GC deleted the blob. Concurrent pins from different module IDs can also overwrite one another's read-modify-write. A pin operation is reasonably expected to atomically establish protection before reporting success.
- **Reachability:** **REACHABLE.** `cache.pin` and `cache.gc` are both registered management operations and module request handlers can run concurrently. The cache is machine-wide, so the same race also exists across module processes; the lease guards only the GC participant.
- **Cost if it fires:** A caller receives a successful pin for an artifact that has been deleted, or a foreign module's pin is lost. The next cold load fails despite the durability promise; if the source is unavailable, this is actual cached-data loss and sustained service refusal.
- **Confidence:** **High.** The two mutation paths plainly lack a common synchronization primitive. A deterministic hook between `pin`'s read and write, paired with zero-grace GC, would raise confidence to a reproduced deletion/lost-update trace.
- **Status:** **VERIFIED.** The management table registers both `cache.pin` and `cache.gc`; `dispatch_request` routes them to independently runnable handlers, and only `gc_digest` previously acquired the digest lease. `pin` now takes the same exclusive digest lease around its metadata read-modify-write, also serializing concurrent pins. Mutation proof: `digest_lease_blocks_pin_metadata_mutation` failed with `assertion failed: matches!(cache.pin(...), Err(ModelCacheError::Lease(LeaseError::Held { .. })))` when the pin lease was removed.

## 4. A second decode request resets an absolute session token ledger to a request-local count

- **Where:** `crates/synapse-module/src/lib.rs:3990-4071` and `crates/synapse-module/src/store.rs:3881-3929`.
- **Actual versus expected:** For every `owned_decode.decode` invocation, the handler initializes `committed` to zero, increments it only with that invocation's generated chunks, and passes it to `commit_serving_session_boundary`. The store documents that parameter as an absolute token count, persists it on the session row, and rejects values lower than the session's previous count. After one successful request, a later request therefore either moves the durable session total backward conceptually or is rejected when its first request-local quantum is smaller than the prior total. The session remains open and clears `active_request` after success, so a reader would expect another decode on the same admitted session to preserve monotonic session accounting.
- **Reachability:** **REACHABLE.** Admit one owned-decode session, complete a decode, then call `owned_decode.decode` again with a new `req_id`. If the first request committed more than `production_n`, the second request's first chunk is necessarily lower and returns `store_failure`; with smaller totals, the row can be overwritten with a non-cumulative count.
- **Cost if it fires:** Valid repeat work is refused, or the durable count used for session status and emergency-revoke terminal accounting understates tokens already emitted. That can make recovery report the wrong prefix and take a revocation decision at the wrong apparent boundary.
- **Confidence:** **High.** The caller's counter scope and the store's monotonic absolute contract directly conflict. An end-to-end two-request session test would raise confidence by pinning the exact wire error and persisted count.
- **Status:** **VERIFIED.** `dispatch_request` routes `owned_decode.decode` to `owned_decode_session_decode`; a completed request clears `active_request`, so a second request reaches the same loop. The store explicitly rejects a boundary below its persisted absolute count, while the handler previously passed its request-local `committed`. The fix reads the durable starting count and adds each request-local boundary. Mutation proof: `second_decode_request_extends_the_absolute_session_boundary` failed with `left: 4, right: 15` when accumulation was replaced by the request-local count.

## 5. Remote 429 backoff ignores the request budget while retaining a provider permit

- **Where:** `crates/synapse-module/src/remote/gateway.rs:492-511`, `crates/synapse-module/src/remote/gateway.rs:638-669`, and `crates/synapse-module/src/remote/classify.rs:45-75`; the caller supplies its budget at `crates/synapse-module/src/lib.rs:6743-6785` and `crates/synapse-module/src/lib.rs:7145-7203`.
- **Actual versus expected:** Every retry passes the original full `remaining_deadline_ms` to pool acquisition instead of subtracting elapsed time. On HTTP 429, an arbitrary `Retry-After` is parsed without a cap and slept before `continue`; the `_permit` acquired for the attempt remains in scope throughout that sleep. There is no outer timeout around the retry loop. A request budget should bound the whole operation, and a request doing pacing backoff should release scarce provider concurrency rather than occupy it while idle.
- **Reachability:** **REACHABLE.** Any configured remote provider can return `429 Retry-After: 86400` to an ordinary `embed.query`, `embed.batch`, or sentinel request. That enters the pacing arm directly; no malformed response or local race is required.
- **Cost if it fires:** The call can remain outstanding far beyond `deadline_ms`. Enough pacing responses occupy every provider permit for the full backoff, refusing unrelated production traffic—including the interactive capacity that the pool is intended to reserve.
- **Confidence:** **High.** Rust drop scope keeps `_permit` alive until the loop iteration ends, and neither the parser nor sleep uses the deadline. A paused-time gateway test could raise confidence to a measured permit starvation and deadline overrun.

## 6. Failed model loads retain their complete scratch downloads indefinitely

- **Where:** `crates/synapse-module/src/lib.rs:6023-6079`, `crates/synapse-module/src/lib.rs:6082-6209`, and `crates/synapse-module/src/lib.rs:6531-6600`.
- **Actual versus expected:** `execute_model_load_job` creates a scratch directory, downloads every asset into it, and removes it only at the end of the success path. Any `?` from download, header validation, cache ingest, package construction, catalog persistence, or worker loading exits the async block and bypasses `remove_dir_all`. The copy loop has no byte ceiling, so a failed package can leave a model-sized or larger tree. Temporary job material should be scoped so both success and failure remove it.
- **Reachability:** **REACHABLE.** Submit `model.load` with a source that downloads successfully but has a wrong digest, invalid tokenizer, invalid artifact header, or engine load failure. The production dispatcher spawns `execute_model_load_job`; after it marks the job failed, no other source path scans or removes `synapse-model-load-*` directories.
- **Cost if it fires:** Repeated failed loads accumulate full model packages in the system temporary volume until disk exhaustion, after which unrelated model loads, cache writes, SQLite writes, or the host service can be refused. The artifacts can also outlive the job's retention policy.
- **Confidence:** **High.** The sole cleanup call is on the success path. A failed-load filesystem assertion would raise confidence to direct runtime evidence and quantify retained bytes.
- **Status:** **VERIFIED.** `model_load` spawns `execute_model_load_job`, whose download, validation, cache-ingest, catalog, persistence, and engine-load failures all use `?`; the only old `remove_dir_all` followed the final successful load. A scoped scratch guard now removes the directory on every exit. Mutation proof: `model_load_scratch_removes_downloads_when_scope_exits` failed with `scratch directory survived guard drop` when cleanup was neutralized.

## 7. Cache ingestion publishes a blob before tokenizer validation, creating invisible, uncollectable orphans

- **Where:** `crates/synapse-core/src/cache.rs:181-226`, `crates/synapse-core/src/cache.rs:228-251`, and `crates/synapse-core/src/cache.rs:357-425`; the model-load caller supplies the tokenizer at `crates/synapse-module/src/lib.rs:6093-6106`.
- **Actual versus expected:** Ingest hashes and renames the source into the permanent blob directory before constructing `SanitizedTokenizer` and before writing metadata. If tokenizer parsing or metadata handling fails, the function returns without removing the newly published blob. Both `gc_all` and `total_blob_bytes` enumerate metadata files rather than the blob directory, so that orphan is neither counted against the watermark nor discoverable by GC. A failed atomic ingest should leave no published cache object, or GC should be able to reconcile it.
- **Reachability:** **REACHABLE.** `model.load` first downloads a tokenizer without validating it, then ingests the model with that tokenizer path. A malformed tokenizer causes `SanitizedTokenizer::from_file` to fail after the entire model blob has already been renamed into cache. The same path is reachable through `cache.pin` with `source_url` plus `tokenizer_path`.
- **Cost if it fires:** Each failure can strand a full model blob permanently outside accounting and reclamation. Repetition fills the cache filesystem even when `cache_max_bytes` and `cache.gc` report that the cache is below its target, eventually refusing production writes or loads.
- **Confidence:** **High.** Publication precedes the fallible validation and the collectors are metadata-driven. A malformed-tokenizer unit test that checks the blob directory before and after GC would provide complete runtime confirmation.
- **Status:** **VERIFIED.** `model_load` downloads the tokenizer without parsing it, then passes that path while ingesting the model; source-backed `cache.pin` passes its `tokenizer_path` to the same ingest method. `gc_all` and `total_blob_bytes` enumerate metadata, confirming that a pre-metadata blob is invisible. Tokenizer sanitization now precedes blob publication. Mutation proof: `ingest_rejects_invalid_tokenizer_without_publishing_blob` failed with `assertion failed: fs::read_dir(root.join(BLOBS_DIR)).unwrap().next().is_none()` when publication was moved back before validation.
